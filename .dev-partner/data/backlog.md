# backlog — 次に作る候補

**区分**
- 【拡張】既存の成果物に機能を足せば済むもの
- 【新規】独立したモノとして作るべきもの
- 【環境】AI自身の開発環境・ツールの改善

判定基準：使う人・使う場面・扱うデータが既存と同じなら【拡張】、違うなら【新規】。迷う場合は両案を書いて比較する。

**価値**（1〜5）
- 1: あれば便利
- 2: 月1回程度の手間が減る
- 3: 毎週の作業が楽になる、または品質が上がる
- 4: 毎週の作業時間が大きく減る、または失敗を確実に防ぐ
- 5: 売上・成果に直結する、またはそれがないと他が進まない

**工数**（1〜5。AIの作業とユーザーの確認を含む）
- 1: 1セッション以内（〜1時間）
- 2: 半日
- 3: 1日
- 4: 2〜3日
- 5: 1週間以上

**優先度** = 価値×2 − 工数
- 高: 6以上
- 中: 3〜5
- 低: 2以下

表には `高(7)` の形で書く。`dp.py score <価値> <工数>` で計算できる。

**状態**：進行中／選択待ち／未着手／保留／完了／見送り

**上位N件の決め方**：進行中 → 選択待ち → 未着手（スコアの高い順）。`dp.py top 3` で表示する。

### B-003 【環境】dev-partner を bon2 以外のセッションやローカルPCでも使えるようにする

- 拡張か新規か: P-000 の改善なので【環境】に分類した。使う人・場面・データは同じ。

### B-004 【拡張】clipper を自分の PC で試す
- 起点: B-001 と B-008 で未検証として残った項目。日本語の文字起こしの精度、実際の動画での採用率、実機の見た目（Edge の窓・SmartScreen の警告からの起動）、Claude 採点、yt-dlp。
- 2026-11-19 の見直し: B-008 でインストーラーができたので、**Claude Code なしで本人が試せる**ようになった。
- 拡張とした理由: 使う人・場面・データは P-002 と同じ。作業は確認と、その結果に応じた調整。
- やること:
  1. ユーザーが `clipper-setup.exe` を入れる（入手先は README）
  2. YouTube Studio から自分の動画と字幕（.srt）をダウンロードし、clipper で候補を作る
  3. 候補を10本以上レビューし、次の4点を教えてもらう
     - 採用した本数（採用率の目標は50%以上）
     - 字幕の誤字の多さ
     - 見た目
     - 使いにくかった点
  4. 結果に応じて、Claude 採点のプロンプト、ルール採点の重み、画面を調整する
     - ユーザーの作業フォルダ（`ドキュメント\clipper\<動画名>.clipper`）を共有してもらえれば、こちらで採点の傾向を分析できる
- 価値5の根拠: 実際の動画で使えるかが分からないと、スタッフへの配布も販売も判断できない。
- 工数1の根拠: ユーザーの作業は30分〜1時間（インストール・候補づくりの待ち時間・レビュー）。調整は1セッション。
- 着手: 2026-11-19「おまかせ」（works/youtube-clipper/B-004/）
- 経過: 2026-11-19、ユーザーの PC で動作を確認できた（1回目は int64 の保存エラー → 修正。2回目はブラウザのダウンロードのブロック → 回避）
- 次のアクション: 採用本数・誤字・見た目・使いにくい点の回答を待つ。確認結果の伝え方 A〜C も選択待ち（推奨 B）

### B-005 【拡張】clipper 第2段階：盛り上がりの信号と、顔を追う縦型切り出し

- 拡張とした理由: 使う人・場面・データ（同じ動画から候補を出す）が P-002 と同じ。
- 改修内容:

  - 変更は `candidates.py` に特徴を3つ、`render.py` にレイアウトを1つ足す程度。中規模
- 価値4の根拠: 配信アーカイブやゲーム実況など、言葉だけでは見どころが拾えない動画に対応できる（Q3 の仮説が外れた場合の備え）。

- 2026-11-19: Twitch のチャットの信号は B-012 に前倒しで移した。この項目に残るのは、音量のピーク・「最も再生された部分」・顔を追う切り出し

### B-009 【拡張】clipper にコード署名を付ける（旧: 配りやすくする）
- 起点: B-008 の配布物は GitHub Actions の成果物（Artifacts）だけで、GitHub へのログインが必要で、保存期間は30日。スタッフに渡すには、ユーザーが一度ダウンロードしてから共有する必要がある。
- 拡張とした理由: 使う人・場面・データは P-002 と同じ。配布の仕組みだけを変える。
- 改修内容:
  - タグを付けると、GitHub Releases にインストーラーを載せる。ワークフローに1ジョブを追加
  - アプリ内に「バージョン表示」と「新しい版があります」のお知らせを付ける（ホーム画面に1行）
  - いずれも小規模
- 注意: bon2 は公開リポジトリなので、Releases も誰でもダウンロードできる。B-003（非公開リポジトリへの移行）を先にするか、Google ドライブなどでの共有と比較して決める。
- 2026-11-19 の見直し: B-004 の実機テストで、ブラウザが「このファイルは危険です」としてインストーラーのダウンロード自体を止めた。非エンジニアのスタッフに「危険なファイルを保存する」操作を頼むのは現実的でない。そのため**コード署名**をこの項目に入れ、価値を3から4に上げた。
  - 証明書の選択肢: OV（年2〜6万円程度。SmartScreen の評価はダウンロード数に応じて徐々に上がる）、EV（さらに高いが、警告がすぐに消える）
  - 署名は CI に組み込む
- 価値4の根拠: 警告がなくならないと、スタッフへの配布ができない。更新の手間もなくなる。
- 工数3の根拠: 証明書の取得（本人確認に数日）、CI での署名、ワークフローと画面の小さな変更。
- 2026-11-19 の分割: 固定ダウンロード先・バージョン表示・更新のお知らせは B-013（アプリ内の更新）に移した。この項目は署名だけにする（価値4・工数3 → 中(5)）
- 次のアクション: B-004 の結果がよく、スタッフに配ると決めたら着手する（証明書の購入はユーザーの判断）

### B-013 【拡張】clipper のアプリ内で更新できるようにする
- 起点: 2026-11-19、ユーザー「修正するたびにアプリをインストールし直す感じ？」。今は直すたびに、GitHub の成果物（ログインが必要・30日で消える）を探してダウンロードし、ブラウザの「危険」警告を通して入れ直す必要がある。
- 拡張とした理由: 使う人・場面・データは P-002 と同じ。配布と更新の仕組みだけを足す。旧 B-009 の「固定ダウンロード先・バージョン表示」もここに含める。
- 改修内容:
  1. main に反映されるたびに、CI が GitHub Releases の「最新版」にインストーラーと版の情報（version.json）を載せる
  2. アプリはホーム画面を開くときに最新版を確認する。新しければ「新しい版があります（日付）→ 更新する」を表示する
  3. 「更新する」を押すと、アプリがインストーラーをダウンロードし、静かに上書きインストールして、自動で開き直す。ブラウザを通さないので「危険」のブロックを受けない
  4. ホーム画面に今の版を表示する
- 注意: bon2 は公開リポジトリなので、Releases のインストーラーは誰でもダウンロードできる。B-003（非公開化）をする場合は、配布先を別に用意する必要がある。
- 価値5の根拠: 試しては直す今の段階で、毎回の入れ直しと警告の操作がなくなる。スタッフへの配布後も更新が楽になる。
