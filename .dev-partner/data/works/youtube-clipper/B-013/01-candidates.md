# B-013 更新の仕組み — 候補（01-candidates）

**状態: 決定（推奨 A）**。2026-11-19 の自動導入の委任（L-013）により、選択を待たずに推奨案で進めた。
- 区分: ロジック系（3案）。比較軸: 更新の手間 × 安全性・作る重さ

| 案 | 内容 | 向くケース | 弱点 | 工数 |
|---|---|---|---|---|
| **A（推奨・採用）** | GitHub Releases に最新版を置く。アプリはホームを開くときに確認し、「新しい版があります → 更新する」を表示。押すとダウンロード → 静かに上書き → 自動で開き直す | 無料で、今の構成のまま足せる。更新するタイミングを人が選べる | Releases は公開になる。B-003 で非公開化するなら置き場所を別に用意する | 半日 |
| B | 起動するたびに、確認なしで自動更新 | 常に最新にしたい | 作業の途中で再起動が起きる。更新に失敗したときに気づきにくい | 半日 |
| C | Microsoft Store や winget で配布し、更新も任せる | 一般向けに販売するとき | 署名・登録・審査が要る（B-009・B-010 の後） | 数日＋登録 |

## A を選んだ理由
- 成功指標の「1クリック・警告0回・失敗しても今の版が残る」を、追加の費用なしで満たせる
- アプリが自分でダウンロードしたファイルにはブラウザの「危険」の印（Mark of the Web）が付かないので、ダウンロード時のブロックも起動時の SmartScreen も出ない
- B は勝手に再起動が起きるのが、レビューの途中の利用者に不親切。C は署名が前提
