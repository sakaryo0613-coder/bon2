# learnings — 成功例・失敗例

着手前（手順0）に必ず読む。この中から今回守るべきものを宣言してから始める。
新しいIDは `dp.py next-id learning` で取得する。

書式:
```
## L-xxx [成功|失敗] 一言タイトル（YYYY-MM-DD / P-xxx or B-xxx）
- 状況:
- 何が起きたか:
- 原因分類: 指示の曖昧さ｜検証不足｜感覚的な調整｜知識不足｜繰り返し作業（成功例は「うまくいった理由」）
- 次回のルール: （次に同じ状況になったら何をするか。1〜2行）
- 対応: （作成・改善したツール、SKILL の変更など。なければ「なし」）
```

## L-001 [成功] 揮発する ~/.claude は実体をリポジトリに置き、リンクで見せる（2026-11-19 / P-000）
- 状況: dev-partner の置き場所に `~/.claude/` を指定された。作業環境はクラウドのコンテナで、セッションが終わると `~/.claude` は消える。
- 何が起きたか: 実体を `bon2/.dev-partner/` に置き、`~/.claude/skills/dev-partner` と `~/.claude/dev-partner` をシンボリックリンクにした。リンクはリポジトリの SessionStart フックが毎回張り直す。
- 原因分類: うまくいった理由は、指定されたパスをそのまま作る前に「その場所はセッションをまたいで残るか」を確認したこと。
- 次回のルール: 永続化が必要なデータを書く前に、置き場所が揮発しないか確認する。揮発するなら Git 管理下に実体を置く。
- 対応: `.dev-partner/install.sh`、`.claude/hooks/dev-partner-session-start.sh`

## L-002 [成功] 公開リポジトリ＋GitHub Pages では作業ファイルをドット始まりのフォルダに置く（2026-11-19 / P-000）
- 状況: bon2 は公開リポジトリで、GitHub Pages が有効（main ブランチの内容が店舗サイトとして公開される）。
- 何が起きたか: 作業ファイルの置き場所を `.dev-partner/` にした。GitHub Pages の Jekyll はドットで始まるフォルダを公開しないので、`.md` が店舗サイトのページとして公開される事故を避けられる。
- 原因分類: うまくいった理由は、置く前に公開範囲（visibility / has_pages）を確認したこと。
- 次回のルール: Webサイトのリポジトリに作業ファイルを置くときは、公開範囲とビルド対象を先に確認する。
- 対応: なし（L-001 と同じ構成で対応済み）

## L-003 [失敗] 新しいセッションは main から始まる。作業ブランチに置いただけでは次に引き継がれない（2026-11-19 / P-000）
- 状況: dev-partner 一式を作業ブランチに push した。SessionStart フックも backlog も作業ブランチにしかなかった。
- 何が起きたか: 新しいクラウドセッションは既定ブランチ（main）を clone するため、そのままでは次のセッションで上位3件の提示も手順も効かないことに、完了報告の直前に気づいた。ユーザーの了承を得て PR を作り main に反映した。
- 原因分類: 知識不足（実行環境がどのブランチからセッションを始めるか）
- 次回のルール: セッションをまたいで使うデータは、区切りごとに PR を作って main に反映する。
- 対応: SKILL「置き場所」に main への反映を追記

## L-004 [失敗] 「おまかせ」の後の後続比較（UIの10案）をやるか迷った（2026-11-19 / B-001）
- 状況: ロジック系の5案から「おまかせ」で案Dに決まった。SKILL には「UIの要素は案を選んだ後に別途比較」と書いてあった。
- 何が起きたか: レビュー画面のUIについて10案を比較するべきか迷った。案Dのファーストビューで画面の方向性はすでに示していたので、省略して進めた。
- 原因分類: 指示の曖昧さ（SKILL 自体の）
- 次回のルール: ユーザーが自分で案を選んだ案件では後続の比較も提示する。「おまかせ」の案件では省略してよく、完了報告にそのことを書く。
- 対応: SKILL 手順2に判断基準を追記

## L-005 [失敗] 見た目の検証漏れと、目視で直す往復（2026-11-19 / B-001）
- 状況: 縦型動画のタイトル・字幕の改行と、レビュー画面のボタン配置。
- 何が起きたか:
  - 改行位置を目で見て1件ずつ直し、4往復かかった（促音・数字・かぎ括弧・送りがな）。
  - 採用/却下ボタンが文字起こしの下に押し出され、1280×800 で画面外にあった（スクショで発見）。
- 原因分類: 感覚的な調整 ＋ 検証不足
- 次回のルール:
  - 微調整が2往復を超えそうなら、例文と期待値の表をテストにするか、tune-panel で数値を並べて調整する。
  - 主要な操作ボタンは `shot.cjs --must-see` で判定する。
- 対応: `tests/test_wrap.py`（改行の表）、`toolkit/tune-panel/`（新規）、`shot.cjs --must-see`（改善）

## L-006 [失敗] 日本語の会話データの性質を知らずにサンプルと規則を作った（2026-11-19 / B-001）
- 状況: 合格基準用のサンプル字幕と、文の区切り・採点の規則を作った。
- 何が起きたか: 次の3件が起きた。
  - 話速を7字/秒と勘で決め、サンプルが短すぎた。
  - 「先生！」の括弧内の！を文末と誤判定した。
  - ルール採点が、2つの話題の特徴を足し合わせた「話題をまたぐ区間」を最高点にした。
- 原因分類: 知識不足
- 次回のルール: 日本語のテキストを扱う案件では、着手前に `knowledge/japanese-text.md` を読む。サンプルの数値は knowledge と実測の値を使う。
- 対応: `toolkit/knowledge/japanese-text.md`、`toolkit/knowledge/short-video.md`（新規）

## L-007 [成功] 守るべき条件をデータ構造で保証した（2026-11-19 / B-001）
- 状況: 成功指標「文の途中で切れない」を、ルール採点・LLM採点・レビュー画面での伸縮のすべてで守る必要があった。
- 何が起きたか: 候補を秒ではなく「文IDの範囲」で表した。その結果、以下が単純になり、3つの経路すべてで境目の条件を満たせた。
  - LLM の応答の検証は、範囲の補正だけで済んだ。
  - 伸縮のUIは文単位のボタンで済んだ。
  - 合格基準のテストも単純になった。
- 原因分類: うまくいった理由は、不変条件を「チェックする」のではなく「表現できないようにする」設計にしたこと。
- 次回のルール: 「〜してはいけない」という合格基準は、まずデータ構造で起こりえないようにできないか考える。
- 対応: なし（設計の指針）

## L-008 [失敗] 対象ユーザーに対して、使い始めの手順が難しすぎた（2026-11-19 / P-002）
- 状況: P-002 の対象ユーザーは「動画編集ソフトの細かい操作はしたくない人」と推定していた。それなのに、起動はターミナルでの `python -m clipper run …` が前提だった。
- 何が起きたか: 完成後、ユーザーから「使い方がよくわからない、起動してほしい」と言われた。合格基準（AC1〜AC12）は機能と品質だけで、「対象ユーザーが自力で使い始められるか」が入っていなかった。
- 原因分類: 検証不足（合格基準に使い始めの手順を含めていなかった）
- 次回のルール: 手順3の合格基準に、使い始めの手順の基準を必ず1つ入れる。例: 非エンジニア向けなら「コマンド入力ゼロで、起動から最初の結果まで3操作以内」。完了報告の使い方は、対象ユーザーが読んで分かる言葉で書く。
- 対応: backlog B-008。SKILL 手順3に追記

## L-009 [失敗] OS・使う人の範囲・目的を推定で置き、3つとも外れた（2026-11-19 / B-008）
- 状況: B-008 の手順1で、仮説を「Mac・自分だけ」とし、目的も実用と考えて推奨を B「Claude に頼むだけ型」にした。
- 何が起きたか: 回答は「Windows・スタッフに配る（好評なら販売）」で、目的は「dev-partner の手順のテスト」だった。推奨は C に変わり、比較ページを作り直した。
- 原因分類: 指示の曖昧さ（推定で済ませてはいけない項目を、推定で済ませた）
- 次回のルール: 「使う人の範囲（自分／社内／販売）」「OS・端末」「目的（本番／試作・テスト）」は、分かっていなければ手順1の質問で優先して聞く。
- 対応: SKILL 手順1に追記

## L-010 [失敗] 外部の依存がある経路を、丸ごと未検証のまま進めた（2026-11-19 / B-001・B-008）
- 状況: この環境からは文字起こしのモデル（huggingface.co）を取得できないため、B-001 では文字起こしを「未検証」として残した。
- 何が起きたか: B-008 の Windows CI で、faster-whisper 1.2.1 と PyAV 19 の組み合わせでは、音声の読み込み（モデルを使わない部分）が必ず失敗すると分かった。どの PC でも起きる不具合で、B-001 の時点でもローカルで再現できた。
- 原因分類: 検証不足
- 次回のルール: モデルや API が使えなくても、それを使わない部分（読み込み・前後処理・呼び出し方）は必ずテストする。本体は、使える環境（GitHub Actions など）で通す。
- 対応: 音声の読み込みを同梱の ffmpeg に変更。`tests/test_whisper_path.py` を追加。SKILL 手順3に追記

## L-011 [成功] 試せない OS（Windows）を、GitHub Actions で検証できるようにした（2026-11-19 / B-008）
- 状況: ユーザーは Windows。この環境は Linux で、.exe を作ることも Windows で動かすこともできない。
- 何が起きたか: GitHub Actions の windows-latest で、テスト → .exe の作成 → 自己テスト → インストーラー → サイレントインストール → 自己テスト → アンインストールまで自動で行った。ユーザーの手を借りずに Windows で動くことを確かめられ、どの OS でも起きる不具合も1件見つかった。
- 原因分類: うまくいった理由は、「検証できない」で止めず、検証できる場所を作ったこと。アプリに `--selftest` を持たせ、同梱物だけで主要な処理を通せるようにしたこと。
- 次回のルール: ユーザーの環境が違うものは、その環境の CI を用意する。配布するアプリには自己テストの入口を必ず作る。
- 対応: `toolkit/knowledge/windows-app.md`、`toolkit/cilog.py`

## L-012 [失敗] 重ね表示（初回ガイド）の重なり順を誤った（2026-11-19 / B-008）
- 状況: レビュー画面に、操作ボタンを強調する4ステップのガイドを重ねて表示した。
- 何が起きたか: 次の2つの不具合が出た。どちらも UI テストで見つかった。
  - 強調した一覧が説明の箱より手前に来て、「次へ」が押せなかった。
  - sticky のヘッダーやパネルが独自の重なり順を作るため、強調したいボタンが暗幕の下に沈んだ。
- 原因分類: 知識不足（CSS のスタッキングコンテキスト）
- 次回のルール: 重ね表示は、暗幕・強調する要素・説明の箱の重なり順を分ける。強調する要素の祖先も前に出す。説明の箱は、強調する場所の反対側に置く。
- 対応: `toolkit/knowledge/web-ui.md`

## L-013 [成功] 委任の範囲を言葉にして記録した（2026-11-19 / P-000）
- 状況: ユーザーから「おまかせでお願いします。必要だと思ったタスクに関しては自動で導入していいよ」と言われた。
- 何が起きたか: 「どこまで任されたか」を SKILL と CLAUDE.md に明文化した。任されたこと（項目の選択と案の選択）と、引き続き確認すること（費用・公開範囲・ユーザーの作業）を分けて書いた。
- 原因分類: うまくいった理由は、委任を「何でもしてよい」と広く解釈せず、取り返しのつかない種類の判断を除外として残したこと。
- 次回のルール: 委任を受けたら、その範囲と除外をすぐ記録する。進めるときは1項目ごとに完了報告を出し、途中で止められるようにする。
- 対応: SKILL「次のモノづくりへのつなぎ」、`.claude/CLAUDE.md`

## L-014 [失敗] 自動の判定が「通った」ことで、見た目の崩れを見落としかけた（2026-11-19 / B-013）
- 状況: ホーム画面の上に「新しい版があります」の帯を足した。`shot.cjs --must-see "#pick,#start"` で主要ボタンがファーストビューに入っているかを判定した。
- 何が起きたか: 判定は OK だったが、スクショを見ると帯が縦に引き伸ばされ、「候補を作る」が下端から26pxまで押し出されていた。画面全体の grid が2行のままで、帯が `1fr` の行に入っていた。スクショを目視して見つけ、直した。
- 原因分類: 検証不足（判定が「入っているか」だけで、「余裕があるか」を見ていなかった）
- 次回のルール: 既存の画面に要素を足したら、足す前と後のスクショを並べて見る。自動の判定は「通ったから見なくてよい」ではなく「見る場所を教える」ものとして使う。
- 対応: shot.cjs に下端の余白の確認（`--edge`、既定48px）を追加。直す前の画面だけに警告が出ることを確認した。knowledge/web-ui.md に grid の行数の注意を追記

## L-015 [成功] 「公開してから試す」ものを、公開前に Windows で丸ごと試せるようにした（2026-11-19 / B-013）
- 状況: アプリ内の更新は、新しい版を公開しないと試せず、失敗するとユーザーの PC のアプリが壊れる。
- 何が起きたか: CI の中で版 0.3.0 の古いインストーラーも作り、入れてから、ローカルの HTTP サーバーで GitHub の Releases と同じ形のデータを見せて更新させた。版が新しくなり、アプリが起動し直すことまで、公開前に Windows で確認できた。
- 原因分類: うまくいった理由は、外部サービス（GitHub API）の接続先を環境変数で差し替えられる作りにしたことと、「古い版」をテストの中で作ったこと。
- 次回のルール: 更新・移行・初回起動のように「前の状態」が要る機能は、テストの中で前の状態を作って通す。外部サービスの接続先は差し替え可能にしておく。
- 対応: `.github/workflows/clipper-windows.yml` の AC5 の手順、knowledge/windows-app.md「アプリ内の更新」
