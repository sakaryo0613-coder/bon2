# learnings — 成功例・失敗例

着手前（手順0）に必ず読む。この中から今回守るべきものを宣言してから始める。
新しいIDは `dp.py next-id learning` で取得する。

書式:
```
## L-xxx [成功|失敗] 一言タイトル（YYYY-MM-DD / P-xxx or B-xxx）
- 状況:
- 何が起きたか:
- 原因分類: 指示の曖昧さ｜検証不足｜感覚的な調整｜知識不足｜繰り返し作業（成功例は「うまくいった理由」）
- 次回のルール: （次に同じ状況になったら何をするか。1〜2行）
- 対応: （作成・改善したツール、SKILL の変更など。なければ「なし」）
```

## L-001 [成功] 揮発する ~/.claude は実体をリポジトリに置き、リンクで見せる（2026-11-19 / P-000）
- 状況: dev-partner の置き場所に `~/.claude/` を指定された。作業環境はクラウドのコンテナで、セッションが終わると `~/.claude` は消える。
- 何が起きたか: 実体を `bon2/.dev-partner/` に置き、`~/.claude/skills/dev-partner` と `~/.claude/dev-partner` をシンボリックリンクにした。リンクはリポジトリの SessionStart フックが毎回張り直す。
- 原因分類: うまくいった理由は、指定されたパスをそのまま作る前に「その場所はセッションをまたいで残るか」を確認したこと。
- 次回のルール: 永続化が必要なデータを書く前に、置き場所が揮発しないか確認する。揮発するなら Git 管理下に実体を置く。
- 対応: `.dev-partner/install.sh`、`.claude/hooks/dev-partner-session-start.sh`

## L-002 [成功] 公開リポジトリ＋GitHub Pages では作業ファイルをドット始まりのフォルダに置く（2026-11-19 / P-000）
- 状況: bon2 は公開リポジトリで、GitHub Pages が有効（main ブランチの内容が店舗サイトとして公開される）。
- 何が起きたか: 作業ファイルの置き場所を `.dev-partner/` にした。GitHub Pages の Jekyll はドットで始まるフォルダを公開しないので、`.md` が店舗サイトのページとして公開される事故を避けられる。
- 原因分類: うまくいった理由は、置く前に公開範囲（visibility / has_pages）を確認したこと。
- 次回のルール: Webサイトのリポジトリに作業ファイルを置くときは、公開範囲とビルド対象を先に確認する。
- 対応: なし（L-001 と同じ構成で対応済み）

## L-003 [失敗] 新しいセッションは main から始まる。作業ブランチに置いただけでは次に引き継がれない（2026-11-19 / P-000）
- 状況: dev-partner 一式を作業ブランチに push した。SessionStart フックも backlog も作業ブランチにしかなかった。
- 何が起きたか: 新しいクラウドセッションは既定ブランチ（main）を clone するため、そのままでは次のセッションで上位3件の提示も手順も効かないことに、完了報告の直前に気づいた。ユーザーの了承を得て PR を作り main に反映した。
- 原因分類: 知識不足（実行環境がどのブランチからセッションを始めるか）
- 次回のルール: セッションをまたいで使うデータは、区切りごとに PR を作って main に反映する。
- 対応: SKILL「置き場所」に main への反映を追記

## L-004 [失敗] 「おまかせ」の後の後続比較（UIの10案）をやるか迷った（2026-11-19 / B-001）
- 状況: ロジック系の5案から「おまかせ」で案Dに決まった。SKILL には「UIの要素は案を選んだ後に別途比較」と書いてあった。
- 何が起きたか: レビュー画面のUIについて10案を比較するべきか迷った。案Dのファーストビューで画面の方向性はすでに示していたので、省略して進めた。
- 原因分類: 指示の曖昧さ（SKILL 自体の）
- 次回のルール: ユーザーが自分で案を選んだ案件では後続の比較も提示する。「おまかせ」の案件では省略してよく、完了報告にそのことを書く。
- 対応: SKILL 手順2に判断基準を追記

## L-005 [失敗] 見た目の検証漏れと、目視で直す往復（2026-11-19 / B-001）
- 状況: 縦型動画のタイトル・字幕の改行と、レビュー画面のボタン配置。
- 何が起きたか:
  - 改行位置を目で見て1件ずつ直し、4往復かかった（促音・数字・かぎ括弧・送りがな）。
  - 採用/却下ボタンが文字起こしの下に押し出され、1280×800 で画面外にあった（スクショで発見）。
- 原因分類: 感覚的な調整 ＋ 検証不足
- 次回のルール:
  - 微調整が2往復を超えそうなら、例文と期待値の表をテストにするか、tune-panel で数値を並べて調整する。
  - 主要な操作ボタンは `shot.cjs --must-see` で判定する。
- 対応: `tests/test_wrap.py`（改行の表）、`toolkit/tune-panel/`（新規）、`shot.cjs --must-see`（改善）

## L-006 [失敗] 日本語の会話データの性質を知らずにサンプルと規則を作った（2026-11-19 / B-001）
- 状況: 合格基準用のサンプル字幕と、文の区切り・採点の規則を作った。
- 何が起きたか: 次の3件が起きた。
  - 話速を7字/秒と勘で決め、サンプルが短すぎた。
  - 「先生！」の括弧内の！を文末と誤判定した。
  - ルール採点が、2つの話題の特徴を足し合わせた「話題をまたぐ区間」を最高点にした。
- 原因分類: 知識不足
- 次回のルール: 日本語のテキストを扱う案件では、着手前に `knowledge/japanese-text.md` を読む。サンプルの数値は knowledge と実測の値を使う。
- 対応: `toolkit/knowledge/japanese-text.md`、`toolkit/knowledge/short-video.md`（新規）

## L-007 [成功] 守るべき条件をデータ構造で保証した（2026-11-19 / B-001）
- 状況: 成功指標「文の途中で切れない」を、ルール採点・LLM採点・レビュー画面での伸縮のすべてで守る必要があった。
- 何が起きたか: 候補を秒ではなく「文IDの範囲」で表した。その結果、以下が単純になり、3つの経路すべてで境目の条件を満たせた。
  - LLM の応答の検証は、範囲の補正だけで済んだ。
  - 伸縮のUIは文単位のボタンで済んだ。
  - 合格基準のテストも単純になった。
- 原因分類: うまくいった理由は、不変条件を「チェックする」のではなく「表現できないようにする」設計にしたこと。
- 次回のルール: 「〜してはいけない」という合格基準は、まずデータ構造で起こりえないようにできないか考える。
- 対応: なし（設計の指針）
